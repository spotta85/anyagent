# Gaps found porting T3 Code to anyagent

Things T3 Code's server needed from its agent layer that anyagent did not have. 26 rows. Each row becomes an anyagent ticket; sizes are estimates in lines of Rust.

Two are bugs found live, not missing features: **Codex ignores declared MCP servers** (flag order, plus the bearer token in argv) and **Quiet codex sessions** (warnings anyagent causes itself). Fix those first.

| Feature | T3 call | What anyagent lacks | Proposed anyagent change | Size (lines) |
|---|---|---|---|---|
| Plan mode | `sendTurn({ interactionMode: "plan" })`; `turn.proposed.delta` / `turn.proposed.completed` events | A normalized plan mode: `mode` values are agent-specific, and no event carries a proposed plan (claude's ExitPlanMode markdown, codex's plan item). Adapter fails plan turns with `ProviderAdapterValidationError` | A well-known `mode` choice `plan` every plan-capable adapter maps, plus `EventKind::PlanProposed { markdown }` | ~80 |
| Accept-edits runtime mode | `startSession({ runtimeMode: "auto-accept-edits" })` | `PermissionMode` is only `Ask` / `AutoApprove`. Adapter opens with `Ask` (stricter: edits still prompt) | `PermissionMode::AcceptEdits`: the engine allows Edit/Delete/Move requests once, forwards the rest | ~25 |
| Per-turn token usage | `turn.completed.payload.tokenUsage` (input, output, cached per turn; feeds T3 turn analytics) | `TurnEnded` carries only `stop`; `ContextUsage` is window fill, not per-turn counts. Adapter omits `tokenUsage`. Live (port-check `usage` row, claude + codex): T3's `context-window.updated` activity gets only `usedTokens`/`maxTokens`, never `inputTokens`/`outputTokens` | `TurnEnded { usage: Option<TurnUsage { input, output, cached_input, reasoning }> }` from claude's result usage and codex's token_count | ~60 |
| Rollback confirmation | `rollbackThread(threadId, n)` returns, then T3 re-binds the session as rewound | `rollback` resolves when the command is forwarded; an agent refusal arrives later as a `Diagnostic`, so T3 believes a refused rollback happened | Reply to `rollback` after the adapter confirms (the `SessionUpdated`), or fail with a typed `RollbackRefused` | ~30 |
| Withdraw a permission request | `respondToRequest(threadId, requestId, "cancel")` | `Answer::Permission` has only Allow/Deny choices; no way to withdraw a request without denying it (ACP's `cancelled` outcome). Adapter sends `DenyOnce` | `PermissionChoice::Cancel` (or `Answer::Withdraw`), mapped to each wire's cancel outcome, falling back to deny-once where none exists | ~20 |
| Per-model option descriptors | `ServerProviderModel.capabilities.optionDescriptors` (T3's picker shows effort/fast per model: haiku has no effort, gpt-6 has `ultra`) | `config_options` describe the session's current model only; `probe` cannot say which options another model choice has. The driver copies the current model's options onto every model | Per-choice options on the `model` option (`ConfigChoice.options: Vec<ConfigOption>`), filled from each catalog T3 already reads (claude `initialize`, codex `model/list`) | ~50 |
| Per-instance binary and environment | Settings `binaryPath`, codex `homePath`/`shadowHomePath`, instance `environment` (`CODEX_HOME`, `GROK_HOME`, API keys). Since Task 4 also: codex and claude `launchArgs`, claude `autoCompactWindow`, cursor `apiEndpoint`, antigravity `authMethod`/`apiKey`/`gcpProject`/`gcpLocation`, opencode `serverUrl`/`serverPassword` (attach to an external server), and the Antigravity runtime T3 installs into its own directory | `AgentRef` is an agent id (or an ACP spec); discovery picks the executable and every session inherits the one `serve` process's env. The driver ignores these settings; each one is a settings field that now does nothing | `AgentRef::Custom { id, path?, env?, args? }` for every adapter, honored by `probe`, `open` and `generate`; for opencode an `attach: { url, password? }` that skips spawning | ~60 |
| Workspace skills | `snapshotForCwd(cwd).skills` (`name, path, scope, enabled`) in the composer's skill picker | `probe` runs in a temp dir and returns `commands` (skills merged in, no path/scope/enabled); nothing per workspace. The snapshot's `skills` is empty | `probe(agent, { dir })` plus `SlashCommand.source: Builtin \| Skill { path, scope }` | ~50 |
| In-app login | `ProviderInstance.auth` (settings "Sign in" button: start a login, show its URL/code, sign out) | `AuthStatus::Unauthenticated` lists `LoginMethod::Terminal { command }` for the user to run; anyagent cannot run a login itself. The snapshot message shows the command | `Runtime::login(agent, method)` streaming `LoginEvent { Url \| DeviceCode \| Done \| Failed }`, and `logout(agent)` | ~120 |
| Redeem a rate-limit reset credit | `ProviderInstance.consumeResetCredit` (claude, codex banked resets) | `plan_usage` reads quota windows only; no account actions | `Runtime::redeem_reset(agent)` for agents whose account API has one | ~40 |
| Images in one-shot generation | `generateBranchName` / `generateThreadTitle` with `attachments` (the old codex generator passed each image with `--image`) | `generate` takes a text prompt only; `prompt` takes attachment paths but `generate` has no such field. AnyagentTextGeneration sends only the prompt text (image names appear in it, not the images) | `generate { attachments: Vec<PathBuf> }`, forwarded like `prompt`'s, gated on `Images` | ~15 |
| Quiet codex sessions | every codex `runtime.warning` becomes a row in T3's work log | Warnings anyagent causes itself reach the caller: the `configWarning` "Under-development features enabled: default_mode_request_user_input" (anyagent sets that flag) on every session open, and after a rollback (`thread/revert`) codex's "recorded with model `gpt-5.6-luna` but is resuming with `gpt-5.6-sol`" (its reload uses the config default) although the next `SessionUpdated` still shows `gpt-5.6-luna` | Drop a `configWarning` that names only flags the adapter set; drop the model-mismatch warning after a revert when the session's model is unchanged (or send the model with the revert if the wire takes one) | ~15 |
| Session instructions | Every old adapter added T3's instructions to each session: runtime info and pull-request linking (`RuntimeInstructions.ts`), and for codex the plan/default collaboration-mode prompt plus the browser and device tool guide (`CodexDeveloperInstructions.ts`) | `open` has no instructions or system-prompt field, so the adapter sends none (both files are kept, unused) | `open { instructions: Option<String> }`, mapped to claude `--append-system-prompt`, codex `developer_instructions` / `additionalContext`, and a first-prompt preamble where the wire has neither | ~40 |
| Feedback upload | `adapter.uploadFeedback({ threadId, reason? })` (the chat view's feedback upload; the old codex adapter sent codex `feedback/upload` for the thread) | No command for it. The adapter leaves `uploadFeedback` undefined, so `ProviderService.uploadFeedback` fails with its typed unsupported error | `Session::upload_feedback { reason }` for agents with such a request (codex) | ~30 |
| Raw wire log | `ProviderEventLoggers.native`: every agent frame per thread, written by the old adapters for debugging | anyagent only surfaces normalized events (and `*/raw_frame` extensions on unmapped-frame diagnostics); the caller cannot record the wire. The native log is no longer written | A `serve --wire-log <dir>` option (or `open { trace: true }` events) that writes each session's frames as NDJSON | ~40 |
| Client MCP servers on opencode and antigravity | Every session gets T3's `t3-code` MCP server (HTTP + bearer header: browser preview, devices, PR linking); the adapter declares it through `open { mcp_servers }` | The opencode adapter refuses client-declared servers ("would need a `POST /mcp` per server after open") and antigravity refuses them (`agy mcp add` only); both advertise no `mcp_transports`, so the adapter skips the declaration and those sessions run without T3's tools. Also: the device tools expect the `agent-device` shim on the agent's PATH (old adapters set it per session), and anyagent has no per-session env (see "Per-instance binary and environment") | opencode: `POST /mcp` per declared server after the session's server is up; antigravity: a per-session config overlay if `agy` has one, else keep refusing | ~50 |
| Codex ignores declared MCP servers | T3's `t3-code` MCP server declared at `open { mcp_servers }` for codex (probe advertises `Stdio`, `Http`) | `mcp_overrides` puts the `-c mcp_servers.<name>.*` overrides before the `app-server` subcommand (`src/adapter/codex.rs` `launch`); codex 0.154.0 honors them for `codex mcp list` but `app-server` never starts the server: no `mcpServer/startupStatus/updated` for it, no request reaches it, no warning. Verified with a wrapper that moves the same args after `app-server`: codex then sends `initialize` to the server. Old T3 passed them after `app-server`. Also: headers go into argv (`-c mcp_servers.<name>.http_headers={Authorization="Bearer …"}`), so the bearer token shows in `ps`; old T3 set `-c mcp_servers.t3-code.bearer_token_env_var="T3_MCP_BEARER_TOKEN"` and passed the token in the app-server's env. Until fixed, T3's adapter declares nothing for codex | Push `app-server` first, then the MCP overrides (as done for `features.default_mode_request_user_input`); send an `Authorization: Bearer <t>` header as `bearer_token_env_var` + a per-server env var in the app-server's environment (other headers stay in `http_headers`); add a live test that a declared HTTP server gets `initialize` and that `ps` shows no token | ~20 |
| Session-free status check | Every snapshot refresh (boot, settings change, periodic, "Refresh") runs `probe` for each enabled kind; T3's rule is that a background health check never opens a session (old Grok probes skipped auth and session creation; Antigravity used initialization only) | `probe` opens a throwaway session in a temp dir and closes it (`src/runtime.rs` `probe`, `docs/core-api.mdx`), so hooks and user-configured MCP servers start on every background refresh. `probe_auth` is cheaper but gives only the login state, not version, models or capabilities | `probe(agent, { depth: Handshake })` that stops after the wire handshake (`initialize` / `--version` + auth read) without `session/new` / `thread/start`, returning what that step learned; models and config options only where the handshake carries them | ~60 |
| Subagent progress | `task.progress` (summary, usage, last tool) and the role, model and effort on `task.started` (claude `task_progress` / `task_notification`, codex collab agents); T3's Agents panel reads them | A subagent is a `Subagent` tool: `ToolUpdated` has its title and status only. The adapter maps `task.started` / `task.completed` from it and drops the subagent's own text (`parent_tool_id` set); no progress rows, no usage. A background agent's tool completes at launch ("Async agent launched"), so its task reads completed while the agent still runs | `ToolUpdate.subagent: Option<SubagentInfo { role, model, summary, usage }>`, filled from claude's task frames and codex's collab agent state | ~50 |
| Live turn diff | `turn.diff.updated { unifiedDiff }` (codex `turn/diff/updated`: the whole turn's diff while it runs) | Tools carry their own `diffs`; codex's turn diff frame is ignored (`src/adapter/codex.rs`). T3 still builds its checkpoint diff when the turn ends; only the live one is gone | `EventKind::TurnDiff { unified }` from codex's frame; other agents leave it off | ~25 |
| Tool denied | `tool.denied { toolName, toolUseId, reason }` (claude `permission_denied`: a rule or hook refused a tool without asking) | A refused tool just ends `Failed`; the reason is lost | `ToolStatus::Denied { reason }` from claude's frame (and ACP's rejected outcome) | ~20 |
| Tool progress | `tool.progress { toolUseId, summary, elapsedSeconds }` (claude `tool_progress`, codex `item/mcpToolCall/progress`) | `ToolUpdated` snapshots have no progress text or elapsed time | `ToolUpdate.progress: Option<String>` (plus `elapsed_ms`) from those frames | ~20 |
| Model rerouted | `model.rerouted { fromModel, toModel, reason }` (codex `model/rerouted`; feeds `ProviderService`'s reroute analytics) | codex's frame becomes a `Diagnostic` warning (text only), so T3 shows a warning and the analytics never see it | `EventKind::ModelRerouted { from, to, reason }` | ~15 |
| Isolated one-shot generation | `generateCommitMessage` / `PrContent` / `BranchName` / `ThreadTitle`. The old claude generator ran with hooks off (`disableAllHooks`), `--strict-mcp-config`, `--tools ""`, `--json-schema`, and titles in a temp dir; codex used `--output-schema` | `generate` opens a tool-less session in the caller's dir with the user's hooks and MCP servers, and has no output schema (T3 digs the JSON out of free text). The adapter now runs titles in a temp dir; commit, PR and branch text still run in the checkout | `generate { isolated: bool, output_schema: Option<Value> }`: no hooks, no user MCP servers, schema passed where the wire takes one (claude `--json-schema`, codex `--output-schema`) | ~50 |
| Cancel a specific or queued turn | `interruptTurn(threadId, turnId)` | `cancel` is session-wide: it stops whatever turn runs and cannot withdraw a queued prompt. The adapter ignores `turnId` | `Session::cancel(target: Option<TurnId \| PromptId>)`: cancel the running turn only if it matches, drop a queued prompt by id | ~30 |
| Narrow `ResumeFailed` | `startSession({ resumeCursor })`; on `ResumeFailed` the adapter opens a fresh session with a warning | codex (`src/adapter/codex.rs` `thread/resume`) and opencode (`src/adapter/opencode.rs` `GET /session/{id}`) map *any* RPC or HTTP error to `ResumeFailed`, so a transient 5xx or connect error drops the conversation as if the agent had forgotten it; claude matches only "No conversation found" | Map only not-found responses to `ResumeFailed`; everything else stays the typed transport/auth error | ~20 |
